# LabelDesk

Платформа двоичной разметки текстов с двумя независимыми аннотациями, разбором
разногласий и ранжированием неопределённых примеров. Включает React-интерфейс
и воспроизводимое сравнение случайной и активной разметки при одинаковом бюджете.
Классы демонстрации: 0 — негативный текст, 1 — позитивный.

## Возможности

- Назначение текста действует 10 минут. На текст назначаются не более двух
  разных участников; участник не может повторно разметить тот же текст.
- Просроченный или использованный токен назначения отвергается. Совпадение двух
  меток утверждает результат; разногласие передаётся администратору.
- Аннотации и решения администратора сохраняются в истории. Изменение решения
  требует текущую версию: устаревший запрос получает 409.
- Пул и контрольная выборка разделены при загрузке. Тексты контрольной выборки
  не выдаются разметчикам и не участвуют в выборе неопределённых примеров.
  Один текст нельзя добавить одновременно в обе выборки.
- TF-IDF и логистическая регрессия обучаются на утверждённых примерах пула.
  `/uncertain` возвращает оставшиеся примеры по близости вероятности к 0,5.
- Симуляция сравнивает две стратегии при равном бюджете, включая два общих
  стартовых примера разных классов. Три фиксированных seed, выбранные ID,
  accuracy, F1 и отпечаток контрольной выборки сохраняются в PostgreSQL.

Стек: Python 3.11+, FastAPI, PostgreSQL 17, scikit-learn, React, esbuild.
`api.py` содержит транзакции назначения и разметки, `learning.py` — модель и
симуляцию, `frontend/app.jsx` — интерфейс. Собранные файлы лежат в
`labeldesk/static`; Docker запускает интерфейс без npm и внешних CDN.

## Запуск

```sh
docker compose up --build -d
curl -H 'X-API-Key: local-demo-key' http://localhost:8092/health
python3 scripts/demo.py
```

Откройте `http://localhost:8092`. Введите `local-demo-key` и свой демонстрационный
идентификатор, затем получите задание и поставьте метку. Для панели администратора
введите `local-admin-key`. Вторую аннотацию можно поставить в другой вкладке
с другим идентификатором. Ключи не сохраняются в localStorage.

Демо загружает 40 синтетических текстов пула и 20 тестовых, затем сравнивает
стратегии при бюджете 12. Повтор демо не создаёт копии текстов. Этот простой набор
проверяет работу контура; он не доказывает преимущество активного обучения.

## API

Обычные операции требуют `X-API-Key`; административные также `X-Admin-Key`.
Схема запросов: `/docs`.

```sh
curl -X POST http://localhost:8092/tasks \
  -H 'X-API-Key: local-demo-key' -H 'X-Admin-Key: local-admin-key' \
  -H 'Content-Type: application/json' \
  -d '{"text":"Доставка прошла отлично","split":"pool"}'
curl -X POST http://localhost:8092/claim \
  -H 'X-API-Key: local-demo-key' -H 'Content-Type: application/json' \
  -d '{"actor":"reviewer-a"}'
```

`POST /annotations` принимает `actor`, `task_id`, `token`, `label` из назначения.
`GET /disagreements` показывает спорные тексты; `POST /tasks/{id}/resolve`
принимает `label` и `revision`. История доступна через `GET /tasks/{id}/history`.
`GET /uncertain` требует утверждённые примеры обоих классов.
`POST /simulate?budget=12` требует эталонные метки всех текстов пула и теста:
это отдельный эксперимент с размеченным набором, а не автоматическая оценка
обычной очереди с неизвестными метками.

## Разработка и тесты

Нужны `uv`, Node.js 22+ для изменения интерфейса и Docker:

```sh
cp .env.example .env
set -a
. ./.env
set +a
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
cd frontend
npm ci --ignore-scripts
npm run build
cd ..
```

После изменения интерфейса пересоберите контейнер: `docker compose up --build -d`.
CI проверяет Python, PostgreSQL-сценарии и воспроизводимость сборки React.
Тесты используют временные схемы БД. Проверяются согласование, история версий,
назначения, изоляция контрольной выборки, равенство бюджета и независимость
выбора обучающих примеров от тестовых меток. Остановка: `docker compose down`.

## Активная очередь и персональные назначения

Разметчику нужны общий `X-API-Key` и персональный `X-Actor-Key`. В Compose настроены
`first` / `local-first-key` и `second` / `local-second-key`. Поле `actor` должно
совпадать с владельцем ключа: подмена второго разметчика отклоняется с 403.
В интерфейсе появилось поле персонального ключа. Ключи задаёт оператор через
JSON-переменную `ANNOTATOR_KEYS`; OAuth и самостоятельной регистрации нет.

Повторный `POST /claim` возвращает незавершённое назначение с тем же токеном.
После перезагрузки страницы введите ключи и снова нажмите «Получить задание»:
повторная выдача не расходует ещё одну задачу.

Администратор создаёт `POST /selection-runs` или нажимает «Обновить активный отбор».
API сохраняет неизменяемый снимок **только пула**: тексты, подтверждённые метки,
ID и ревизии. Эталонные метки и тестовые тексты не попадают в обучение отбора.
Фоновый `worker` обучает TF-IDF + LogisticRegression и атомарно сохраняет порядок
по неопределённости. `GET /selection-runs/{id}` показывает статус, хеш снимка и
порядок. Одинаковый снимок возвращает тот же запуск.

Очередь назначений использует последнюю завершённую версию, затем новые тексты,
отсутствующие в снимке. Уже размеченные и занятые задания фильтруются при выдаче.
Ответ назначения содержит `selection_run`, поэтому порядок можно объяснить
конкретным снимком. После новой разметки администратор явно обновляет отбор;
уже выданные задания не переставляются.

Воркер удерживает сессионную advisory lock на запуске, но не транзакцию обучения.
При завершении процесса блокировка освобождается, незавершённый снимок остаётся
в очереди. Ранжирование и статус фиксируются вместе. Позднее завершившийся старый
запуск не вытесняет более новую завершённую версию. Ошибка данных оставляет `failed`
без частично опубликованного порядка; измените данные, чтобы создать новый снимок.

`GET /agreement` показывает долю согласия и каппу по парным аннотациям. Это сводная
диагностика при разных парах участников; качество каждого разметчика отдельно не
оценивается. Для единственного общего класса каппа не определена и возвращается null.

## Ограничения

Максимум 2000 текстов, два класса и две аннотации на задачу. Распределение
сериализовано PostgreSQL. Модель активного отбора обучается в памяти фонового
воркера; симуляция по-прежнему синхронная. Веса классификатора не экспортируются,
но входной снимок и окончательный порядок сохраняются. При обновлении библиотек
повторное обучение может изменить численные результаты.

Аннотации неизменяемы; исправления делает администратор с историей решений.
Поиск близких перефразировок между пулом и тестом не реализован. Синтетический
набор слишком прост для выводов о преимуществе активного обучения на реальных
данных. Для внешнего развёртывания замените демонстрационные ключи и настройте TLS.
